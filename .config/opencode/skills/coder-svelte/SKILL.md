## Project Scaffolding

To initialize a new project:

```bash
# Create a new SvelteKit project
bunx sv@latest create --template minimal --types ts paraglide="languageTags:en,<LANGUAGE_1>,<LANGUAGE_2>+demo:no" mdsvex --install bun <MY-SITE>
cd <MY-SITE>

bun add --dev @types/bun unocss @unocss/astro @unocss/preset-wind4 @unocss/preset-icons
bun svelte-kit sync
```

Create `uno.config.ts`:

```ts
import { defineConfig, presetWind4, presetIcons } from 'unocss';

export default defineConfig({
  presets: [
    presetWind4(),
    presetIcons(),
  ],
});
```

Add to `vite.config.ts`: 

```ts
import { sveltekit } from '@sveltejs/kit/vite';
import UnoCSS from '@unocss/svelte-scoped/vite';
import { defineConfig } from 'vite';

export default defineConfig({
  plugins: [
    UnoCSS({ injectReset: true }),
    sveltekit(),
  ],
});
```

## Svelte 5 Fundamentals

### File Structure of a `.svelte` Component

Follow this order inside every `.svelte` file:

```svelte
<!-- 1. Script block (always lang="ts") -->
<script lang="ts">
  // a. Imports
  // b. Props interface + $props()
  // c. Local state ($state, $derived)
  // d. Effects ($effect)
  // e. Functions / handlers
  // f. Snippet definitions only when they need script-scope variables
</script>

<!-- 2. Template (HTML) -->

<!-- 3. Styles (only when UnoCSS utilities are insufficient) -->
<style>
  /* scoped styles */
</style>
```

### Runes — the only reactivity model

- **Always** use runes (`$state`, `$derived`, `$effect`, `$props`, `$bindable`). Never use the legacy `let`-based reactivity, `$:` reactive statements, or `export let`.
- Declare reactive state with `let count = $state(0)`, not `let count = 0`.
- Prefer `$derived(expr)` over `$effect` when the goal is computing a value from other reactive values. `$effect` is for side-effects only (DOM manipulation, logging, timers, fetching as last resort).
- Never read **and** write the same `$state` inside a single `$effect` — this creates infinite loops.
- Use `$state.raw(value)` for large, immutable data structures (e.g., lists fetched from an API) where deep reactivity is unnecessary.
- Use `$state.snapshot(value)` when you need to pass a deep-reactive object to external code that expects a plain object (e.g., `structuredClone`, `JSON.stringify`, or third-party libs).

### Props

- Declare props with `let { foo, bar = 'default' }: Props = $props()`. Always type with an interface or type alias named `Props` defined above.
- For bindable props, use `let { value = $bindable('') }: Props = $props()`.
- Spread remaining props with `let { class: className, ...rest }: Props = $props()` and forward them to the root element.
- Never destructure `$props()` in a second step — do it in a single declaration.

### Snippets, not slots

- Svelte 5 replaces slots with **snippets**. Never use `<slot>` or `$$slots`.
- Define reusable markup with `{#snippet name(params)}...{/snippet}` and render with `{@render name(params)}`.
- Accept children content via a `children` snippet prop: `let { children }: Props = $props()` then `{@render children?.()}`.
- For named projection, accept additional snippet props (e.g., `header`, `footer`) typed as `Snippet<[arg?: T]>` from `'svelte'`.

### Event handling

- Svelte 5 uses standard HTML event attributes: `onclick`, `onkeydown`, etc. Never use the legacy `on:click` directive.
- For component-level callbacks, pass them as regular props (`onchange`, `onsubmit`). There is no `createEventDispatcher`.
- Always type callback props explicitly (e.g., `onchange?: (value: string) => void`).

### Control flow

- Use `{#each items as item (item.id)}` — **always** provide a key expression to optimize UI performance.
- Prefer `{#if}` / `{:else if}` / `{:else}` blocks. Avoid hiding logic in ternary expressions inside templates when there is substantial markup.
- Use `{#await promise}` for async rendering in templates only for simple, non-critical data. Prefer SvelteKit `load` functions for anything important.
- Use `{#key expression}` to force re-creation of a component or DOM subtree when a value changes. Use only if required.

## SvelteKit Architecture

### Routing & load functions

- Use file-based routing under `src/routes/`. Every route folder gets a `+page.svelte` and, when data is needed, a `+page.server.ts` (preferred) or `+page.ts`.
- **Default to `+page.server.ts`** for `load` functions — keeps secrets, DB calls, and tokens on the server. **Never** share secrets with the client-side (browser), unless it's a user-specific secret that he is allowed to know without compromising security.
- Use `+page.ts` only when the load function needs to run on both server and client (e.g., purely public API calls that benefit from client-side navigation).
- Always type load return values. Use `PageServerLoad` / `PageLoad` from `./$types` (auto-generated).
- Access parent data with `await parent()` sparingly — prefer flat data shapes.
- Never use `fetch` from the global scope inside `load`; always use the `fetch` provided by the `load` event.

### Layout hierarchy

- Place shared chrome (header, nav, footer) in `+layout.svelte`. Keep layouts thin — no heavy logic.
- Use `+layout.server.ts` to load session/user data once at the root and cascade it down.
- Group routes with `(group)` folders to apply layouts without affecting the URL path.

### Form actions

- Use SvelteKit **form actions** (`+page.server.ts` → `export const actions`) for all mutations (create, update, delete). Never `POST` from the client manually, because loading a new page using `POST` breaks backward navigation in the browser.
- Always validate inputs server-side inside actions, because the tech-savvy users can tweak their browser to bypass client-side checks.
- Return `fail(400, { errors })` for validation problems — never throw redirects as errors inside actions; use `redirect(303, '/path')` from `@sveltejs/kit`.
- Use `enhance` from `$app/forms` on `<form>` elements to get progressive enhancement with SPA-like feedback. Provide a callback to `enhance` when you need loading states or optimistic UI.

### API routes

- Place API endpoints in `+server.ts` files. Export named functions: `GET`, `POST`, `PUT`, `DELETE`.
- Always return `json(data)` or `new Response(...)` with proper status codes.
- Never use API routes for things that form actions can handle (i.e., page-specific mutations).
- Use API routes for third-party webhook receivers, programmatic/non-browser clients, and streaming responses.

### Hooks

- `src/hooks.server.ts` is the middleware layer. Use `handle` to parse cookies, attach user data to `event.locals`, set security headers.
- Chain multiple concerns with `sequence()` from `@sveltejs/kit/hooks`.
- Use `handleFetch` only when you need to rewrite or authenticate internal fetch calls during SSR.

### Environment variables

- Use `$env/static/private` for build-time private secrets (e.g., `IDP_CLIENT_SECRET`).
- Use `$env/static/public` for build-time public values (prefixed `PUBLIC_`).
- Use `$env/dynamic/private` and `$env/dynamic/public` when the value must be read at runtime (e.g., container deployments where env vars aren't known at build time).
- Never import from `$env/static/private` or `$env/dynamic/private` in client-side code — SvelteKit will error, but be intentional.

## Component Patterns

### File structure

- One component per file. Name with PascalCase: `UserCard.svelte`.
- Co-locate component-specific types in the same file or in a sibling `types.ts` when shared.
- Place shared components in `src/lib/components/`, domain components near their route.

### Styling with UnoCSS

- Use the Wind4 Preset of UnoCSS to offer compatibility with Tailwind CSS v4 utilities.
- Use UnoCSS utility classes directly in markup. Do not use Svelte's `<style>` block unless you are wrapping a third-party element that cannot accept classes.
- Accept a `class` prop in every reusable component, rename to `className` internally, and merge with defaults using the `clsx()` utility.
- Never use `@apply` in component styles — it defeats the purpose of utility-first CSS.
- Use UnoCSS' design tokens (`text-sm`, `p-4`, `rounded-lg`) consistently. Do not hard-code pixel values.

### Bits UI (headless components)

- Import only the compound-component parts you need: `import { Dialog } from "bits-ui";` then use `<Dialog.Root>`, `<Dialog.Trigger>`, `<Dialog.Content>`, etc. This allows Tree shacking.
- Apply all visual styling via UnoCSS classes on Bits UI elements. Bits UI provides behavior and accessibility — you provide the look.
- Leverage the `asChild` snippet pattern when you need Bits UI behavior on a custom element.
- Use the component's `on*` callback props and state-binding props (e.g., `bind:open`) for control. Check the Bits UI v1 docs — it follows Svelte 5 conventions (snippets, runes).
- For transition/animation on Bits UI overlay components, use Svelte's `transition:` directive or CSS transitions on the content wrapper — Bits UI does not impose any transition.

### Accessibility

- Let Bits UI handle ARIA roles and keyboard nav for complex widgets (dialogs, menus, popovers). Do not re-implement.
- For custom interactive elements, always add `role`, `aria-label`, and keyboard handlers.
- Use semantic HTML (`<nav>`, `<main>`, `<article>`, `<section>`) before reaching for ARIA.

## Multilingual Website (i18n)

### Recommended approach: Paraglide.js (by Inlang)

Paraglide generates fully typed, tree-shakeable message functions at build time. It is the best-integrated i18n solution for SvelteKit.

### Setup

- Install `@inlang/paraglide-sveltekit`.
- Define messages in `messages/{lang}.json` (e.g., `en.json`, `it.json`, `de.json`) using Paraglide's ICU-like syntax.
- Configure available and default languages in `project.inlang/settings.json`.

### Routing strategy

- Use Paraglide's SvelteKit plugin which adds a `[lang]` prefix strategy automatically via the `reroute` hook and a `handle` hook.
- Links are automatically localized — use `<a href="/about">` and the plugin rewrites to `/en/about`, `/it/about`, etc.
- The default language can be configured to have no prefix (e.g., `/about` = English, `/it/about` = Italian).

### Usage in components

- Import messages as functions: `import * as m from '$lib/paraglide/messages';`.
- Use in markup: `<h1>{m.homepage_title()}</h1>`.
- For messages with parameters: `{m.greeting({ name: user.name })}`.
- Messages are typed — a typo or missing param is a compile-time error.
- Access the current language with `languageTag()` from `$lib/paraglide/runtime`.

### Language switcher

- Build a language switcher component using `i18n.route(canonicalPath)` from the Paraglide SvelteKit integration to compute the equivalent path in another locale.
- Use `<a>` tags (not programmatic navigation) so that the middleware handles the locale transition.

### Server-side concerns

- In `+page.server.ts` / `+layout.server.ts`, read the current language from `event.locals.paraglide.lang` (set by the Paraglide handle hook).
- When returning user-facing error messages from the server, pass message keys (not translated strings) and translate on the client. Alternatively, use Paraglide on the server with `setLanguageTag()` scoped to the request.
- Set `<html lang="{languageTag()}">` in `app.html` dynamically via the Paraglide hook — it handles this automatically.

### Content & SEO

- Paraglide injects `<link rel="alternate" hreflang="...">` tags automatically.
- Write `<svelte:head>` meta titles and descriptions using message functions.
- Use `{@html}` only for rich-text translations where absolutely necessary — sanitize first.

## User Session & Authentication

### Architecture overview

Authentication is offloaded to **Zitadel** (or Google via Zitadel as an IdP). The SvelteKit app never handles passwords. The flow is:

1. User clicks "Sign in" → redirected to Zitadel's hosted login.
2. Zitadel authenticates and redirects back with an authorization code.
3. SvelteKit's **callback route** exchanges the code for tokens server-side.
4. Tokens are stored in **httpOnly, secure cookies** — never in localStorage.
5. Every request reads cookies in `hooks.server.ts`, validates the session, and populates `event.locals.user`.

### Cookie configuration

- Set cookies with these flags **always**: `httpOnly: true`, `secure: true`, `sameSite: 'lax'`, `path: '/'`.
- Store the **access token** in a cookie named `session_token` (encrypted or opaque reference to server-side storage).
- Store the **refresh token** (if used) in a separate cookie with a longer `maxAge` — still `httpOnly` and `secure`.
- **Never** store tokens in cookies readable by JavaScript. **Never** send tokens to the client in page data.
- Set reasonable `maxAge` values: access token cookie ≈ 15–30 min, refresh token cookie ≈ 7–30 days.

### OIDC flow implementation

- Use a lightweight OIDC client lib (e.g., `openid-client` or `arctic`) to handle the protocol — do not hand-roll token exchange or JWT verification.
- Create three server routes:
  - `GET /auth/login` — generates a random `state` + `code_verifier` (PKCE), stores them in a short-lived httpOnly cookie, and redirects to Zitadel's `/authorize` endpoint.
  - `GET /auth/callback` — receives the authorization code, validates `state`, exchanges the code for tokens, sets session cookies, and redirects to the app.
  - `POST /auth/logout` — clears session cookies and calls Zitadel's `/end_session` endpoint.
- Store `state` and `code_verifier` in a temporary httpOnly cookie (not in query params or localStorage).

### Session resolution in hooks

```ts
// src/hooks.server.ts — simplified structure
export const handle: Handle = async ({ event, resolve }) => {
  const token = event.cookies.get('session_token');
  if (token) {
    const user = await validateAndDecodeToken(token); // verify JWT sig + exp
    if (user) {
      event.locals.user = user; // { id, email, roles, scopes }
    } else {
      // Token expired → attempt silent refresh if refresh_token cookie exists
      const refreshed = await tryRefresh(event.cookies);
      if (refreshed) event.locals.user = refreshed.user;
    }
  }
  return resolve(event);
};
```

- Type `event.locals` in `src/app.d.ts`:

```ts
declare global {
  namespace App {
    interface Locals {
      user: { id: string; email: string; roles: string[]; scopes: string[] } | null;
    }
  }
}
```

### Protecting pages (server-side)

- In `+page.server.ts` or `+layout.server.ts`, check `event.locals.user` at the top of every `load` function.
- If the user is not authenticated, throw `redirect(303, '/auth/login')`.
- If the user lacks a required role/scope, throw `error(403, 'Forbidden')`.
- **Never** rely solely on client-side checks to hide pages — always enforce on the server.

```ts
// src/routes/(protected)/dashboard/+page.server.ts
export const load: PageServerLoad = async ({ locals }) => {
  if (!locals.user) throw redirect(303, '/auth/login');
  if (!locals.user.scopes.includes('read:dashboard')) throw error(403, 'Forbidden');
  // ... load data
};
```

### Protecting page groups with layouts

- Use a route group like `(protected)` with a `+layout.server.ts` that enforces authentication once for all child routes.
- Child `+page.server.ts` files then only need to check for specific roles/scopes, not re-check auth.

```ts
// src/routes/(protected)/+layout.server.ts
export const load: LayoutServerLoad = async ({ locals }) => {
  if (!locals.user) throw redirect(303, '/auth/login');
  return { user: locals.user };
};
```

### Checking user identity & scopes in the client

- Page data flows down from the layout `load` → `$page.data.user` is available everywhere.
- Use this **only for UI rendering** (showing/hiding elements, displaying user info).
- Example: `{#if $page.data.user?.scopes.includes('write:posts')}<button>New Post</button>{/if}`.
- **This is not a security boundary** — the server must independently verify permissions for every mutation and data load.

### Protecting API routes

- In `+server.ts`, read `event.locals.user` (populated by the hook) before doing anything.
- Return `401` if no user; `403` if the user lacks the required scope.

```ts
export const POST: RequestHandler = async ({ locals, request }) => {
  if (!locals.user) return json({ error: 'Unauthorized' }, { status: 401 });
  if (!locals.user.scopes.includes('write:items')) return json({ error: 'Forbidden' }, { status: 403 });
  // ... handle request
};
```

### Utility: auth guard helpers

- Create `src/lib/server/auth.ts` with reusable helpers like `requireUser(locals)` and `requireScope(locals, scope)` that throw the appropriate redirect/error.
- Use these one-liners in load functions and API routes to keep code DRY.

### Security checklist

- [ ] All cookies: `httpOnly`, `secure`, `sameSite: 'lax'`.
- [ ] PKCE (`code_verifier` + `code_challenge`) for the OIDC flow.
- [ ] `state` parameter validated on callback to prevent CSRF.
- [ ] Tokens never exposed to client JS — no `$page.data.accessToken`, no `localStorage`.
- [ ] JWT signature verified on every request (use Zitadel's JWKS endpoint, cache the keys).
- [ ] Refresh tokens rotated on use (configure in Zitadel).
- [ ] Set `Content-Security-Policy`, `X-Frame-Options`, `X-Content-Type-Options` headers in hooks.
- [ ] CSRF protection: SvelteKit handles this automatically for form actions; for custom API routes, verify `Origin` header.
- [ ] No `$env/static/private` imports in client-reachable modules.
- [ ] Auth checks happen server-side (`locals.user` in load/actions/API), never client-only.

## Performance & SSR Guidelines

- Use `$state.raw()` for large data sets returned from load functions.
- Avoid `$effect` on the server — it only runs client-side. If you need server-side computation, use `$derived` or put it in the load function.
- Use `{#key expression}` sparingly — it destroys and recreates DOM. Prefer reactive updates.
- Lazy-load heavy components with dynamic imports:

```svelte
{#await import('$lib/components/heavy-chart.svelte') then { default: Chart }}
  <Chart {data} />
{/await}
```

- Use `loading="lazy"` and `decoding="async"` on below-the-fold images.
- Use SvelteKit's `preload` for critical navigation:

```svelte
<a href="/dashboard" data-sveltekit-preload-data="hover">Dashboard</a>
```

### Responsive & Accessible

- Mobile-first: write base styles for small screens, use `sm:`, `md:`, `lg:` for larger breakpoints.
- Prefer `gap-*` over margins for spacing between flex/grid children.
- Use semantic elements (`<nav>`, `<main>`, `<section>`, `<article>`). UnoCSS doesn't replace HTML semantics.

### Dark Mode

If a dark version of the website is requested:
- Use UnoCSS Wind4's `dark:` variant with the `class` strategy (toggled via a `.dark` class on `<html>`).
- Always specify both light and dark variants for colors that differ between modes.

## Bun Runtime

- Use `bun` as the runtime and package manager. Run the dev server with `bun run dev` and build with `bun run build`.
- Use `svelte-adapter-bun` (community adapter) for production builds. It replaces `"@sveltejs/adapter-auto"` in `svelte.config.js`.
- Prefer Bun's built-in APIs (`Bun.serve`, `Bun.file`, `Bun.password`) in server-only code (`+server.ts`, `+page.server.ts`, hooks) when they offer a meaningful advantage (e.g., `Bun.password.hash` for hashing).
- Never import Bun-specific APIs in shared or client code — it will break the browser build. Favor standards-based APIs for code shared between client-side and server-side.

## Code Quality Rules

- [ ] **No `any`** — use `unknown` and narrow with type guards.
- [ ] **No `// @ts-ignore`** or `// @ts-expect-error` without an accompanying explanation comment.
- [ ] **No barrel files** (`index.ts` re-exporting everything) — they hurt tree-shaking and slow down Bun's module resolution.
- [ ] **Prefer `$effect` cleanup** — always return a cleanup function from `$effect` when registering listeners or timers.
- [ ] **No direct DOM access** unless absolutely necessary. Use `bind:this` to get element references; never `document.querySelector`.
- [ ] **Error handling** — wrap external calls (`fetch`, DB) in try/catch inside server load functions; return meaningful error shapes.
- [ ] **Keep components under ~150 lines.** Extract logic into `.svelte.ts` files using rune-based reactive classes or functions when state logic grows.
